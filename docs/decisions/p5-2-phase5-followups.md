| # | Decision | Reasoning |
|---|---|---|
| O-8 | Health checks are our own `ISystemHealthCheck`, not `Microsoft.Extensions.Diagnostics.HealthChecks`. The assembly that owns what is checked implements and registers its checks, scoped; AI keys now lives in `Noof.Ledger.Ai`. One DI scope per run, so the checks run one at a time — today's `HealthCheckService` used a scope per check and ran them in parallel; this is a choice, reversible inside `SystemHealth`. A 5 s cooperative per-check timeout; Disk reads free space off-thread so it can be abandoned. Summaries show the exception type, never its message. A composition test on the real host replaces the central name and category lists | Operator's PR #1 decision: health checks are our own seam. Sharing one scope keeps the checks as plain constructor-injected classes at the cost of running them sequentially instead of in parallel; a repo that is public should never echo a raw exception message to `/diagnostics`, the dashboard tile or Telegram `/health` |
| O-9 | The runtime database log level is persisted in a new table, `app_setting` (`key`/`value`/`updated_at`), not reused from `app_secret` and not written to a file under `%LOCALAPPDATA%` | `app_secret` carries encrypted-secret semantics and is shown on the Secrets page — wrong shape for a plain enum. A file under `%LOCALAPPDATA%` would split state between disk and database and is not in `pg_dump` backups. *(Amended, Phase 5 final review: the original reasoning's "the database sink cannot write before Ready anyway" stopped being true once `ReadyGatedBufferSink` started buffering pre-Ready events for a flush-on-Ready — a stored `Off`/`Warning`/etc. now has to be loaded and applied to the buffer's own level switch before that flush, or the startup burst reaches `app_log` regardless of what is stored. `ReadyGatedBufferSink` takes a `loadDatabaseLevelAsync` delegate for exactly this, invoked (and awaited) only once the gate turns Ready and re-filtering every buffered event against the now-current level before it is released.)* |
| O-10 | The root Serilog level is `min(file floor, console floor, database level unless Off)`, controlled by a `LoggingLevelSwitch`, rather than a root fixed at Verbose with per-sink filters alone | An event is only created when some sink wants it — keeping the root no higher than necessary keeps `IsEnabled` cheap everywhere nothing asked for Debug. Consequence: an `Override` set below a sink's own floor no longer reaches that sink (e.g. an EF Command override at Debug with a file floor of Information stops putting SQL in the file) — harmless today because the checked-in `Logging:File:MinimumLevel` is `Debug` |
| O-11 | *(Superseded 2026-09-26 by decision (a) in `p5-3-log-settings.md` — the operator withdrew the cap.)* The Logs page's "Record to database from" control offers only Verbose, Debug and Information — never Warning or above | `/transactions/{id}/trace` and its stage summary are built from Information-level stage events (5001–5005, 5009); allowing Warning+ would silently empty the trace page for anyone who chose it |
| O-12 | Every timed operation goes through `IOperationTimer`/`OperationTiming`, never `Stopwatch` or a `GetUtcNow()` subtraction, with thresholds keyed by name (exact match, then the text before the first `.`, then `default`) in `Logging:SlowOperationMs`, and a Telegram long poll's threshold is `Telegram:PollingSeconds` plus the `telegram` key so raising the poll interval can never turn idle polls into Warnings | `TimeProvider.GetTimestamp`/`GetElapsedTime` is the one mechanism every other timed test in this repo already trusts; a static threshold for the long poll would make its own configuration setting silently produce false Warnings |
| O-13 | Queue wait (`job.queueWait`) is measured as `job.ClaimedAt - job.CreatedAt`, not against a dedicated `enqueued_at` column | Fixed (final review, major): the first cut used `job.RunAfter`, but `EfJobQueue.ClaimAsync` rewrites `run_after` to the lease expiry as part of the same UPDATE that claims the row, so `RunAfter` is *never* the time the job became due - the measured wait was `-Lease` (a constant negative number) on every job, first attempt included, not only on a re-claim as first written here. `CreatedAt` is stamped once at enqueue by every job-creating call (`EfCaptureStore`, `EfRecordEditor`, `EfTranscriptionStore`) and never touched by `ClaimAsync`/`RetryAsync`/`ReleaseExpiredLeasesAsync`, so it needed no schema change and no new column - `EfJobQueueTests.A_reclaim_after_the_lease_expires_leaves_CreatedAt_untouched` proves it survives a release-and-reclaim cycle |
| O-14 | Each health check's `health.<Name>` timing (and the run's own `health.run`) is logged under `SystemHealth`'s own category (`Noof.Ledger.Host.Diagnostics.SystemHealth`), never the check's own `LogCategory` | The checked-in `Serilog:MinimumLevel:Override:Microsoft.EntityFrameworkCore=Information` would otherwise silently drop the Migrations check's Debug timing, since it shares that category |
| O-15 | Npgsql does not log through the app's `ILoggerFactory`: at database level Debug, after a real `DbContext` round trip, zero `app_log` rows carry a source starting with `Npgsql` (`DatabaseLogLevelDbTests`) | No `Serilog:MinimumLevel:Override:Npgsql` was added, per operator question 7's own "yes, but only if they are found" — the guard test that would have detected rows was deleted rather than kept never-red; a future EF/Npgsql upgrade that changes this needs to be caught again by hand (`docs/backlog/loose-ends-phase-5-observability.md`) |
