# Phase 6 — Receipts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Task briefs are requirement briefs: design the code within them, following the repo's patterns, strict TDD.

**Goal:** A photographed Serbian fiscal receipt (or its QR link) becomes one transaction whose line items are the receipt's lines in order, categorised, with one merchant — from the Tax Administration's data when the QR reads and the site answers, from a vision model otherwise, with every degraded path visible.

**Architecture:** Facts from C# (`Noof.Ledger.Receipts`: QR reading, offline `vl` decoding, the Tax Administration client, the journal parser); the model only categorises lines and, as a fallback, reads the photo. Receipts are evidence tables (`receipts`, `receipt_lines`); line items reference them.

**Tech Stack:** .NET 10, EF Core + PostgreSQL, ZXing.Net + ImageSharp bindings, Microsoft.Extensions.AI (Anthropic), Telegram.Bot, Blazor.

**Spec:** `docs/superpowers/specs/2026-09-25-receipts-design.md`. Shared contract: `src/Noof.Ledger.Application/Receipts/ReceiptContracts.cs` (commit 9b81476).

**Waves:** 1 = Tasks 1 (data), 2 (Receipts library), 3 (Ai) in parallel. Wave 2 = intake + extraction worker + categorisation/echo + UI/health, briefed after wave 1 merges against the real code.

## Global Constraints
- CLAUDE.md is binding (money decimal; public via interfaces + AddNoofXxx; minimum accessibility; [LoggerMessage] in sibling top-level classes; migrations file-scoped; tests on template clones; never noof_ledger).
- Synthetic fixtures only: no real receipt, real shop PIB or real `vl` enters the repo.
- The full `vl` is never logged (first 8 characters at most).
- The model never produces an amount for a fiscal-QR receipt; amounts come from `receipt_lines`.

### Task 2: Noof.Ledger.Receipts — fiscal QR decoding, QR reading, Tax Administration client, journal parser

Spec: docs/superpowers/specs/2026-09-25-receipts-design.md §3 (binding). Shared contract on the branch: src/Noof.Ledger.Application/Receipts/ReceiptContracts.cs — implement `IFiscalQrDecoder`, `IQrReader`, `IFiscalReceiptClient` exactly as declared; do not redefine the records.

The project src/Noof.Ledger.Receipts exists (refs Application, Domain) with no code. Add a test project tests/Noof.Ledger.Receipts.Tests (xUnit v3 on MTP like the others, AwesomeAssertions; add it to NoofLedger.slnx; InternalsVisibleTo). Add `AddNoofReceipts(this IServiceCollection)` registering the three services and a typed HttpClient; call it from Host's composition (Program.cs through the existing registration pattern — Program names no implementation type). Update the architecture tests that enumerate assemblies/projects (project reference rules, PublicSurfaceTests allowlist for the registration class, Web must not reference Receipts).

1. `FiscalQrDecoder : IFiscalQrDecoder` — URL must be https on suf.purs.gov.rs with path /v/ and a `vl` query value (URL-decoded, spaces tolerated). Base64 → bytes (572–848 bytes). Layout (ported from turanjanin/serbian-fiscal-receipts-parser, MIT — credit it in a one-line comment with the link): byte 0 version; 1..8 requestedBy (ASCII); 9..16 signedBy (ASCII); 17..20 totalCounter (uint32 LE); 21..24 transactionTypeCounter (uint32 LE); 25..32 totalAmount (int64 LE, /10000 → decimal RSD); 33..40 dateTime (int64 **big-endian**, Unix milliseconds → DateTimeOffset UTC); 41 invoiceType (0 Normal,1 Proforma,2 Copy,3 Training,4 Advance); 42 transactionType (0 Sale,1 Refund); 43 buyerIdLength; buyerId; then encryptedInternalData (512 bytes if total length > 592 else 256); signature 256; last 16 bytes = MD5 of everything before. Map (invoiceType, transactionType) → contract ReceiptKind (Normal+Sale → Sale, Normal+Refund → Refund, Copy → Copy, Training → Training, Proforma → Proforma, Advance → Advance). Any malformation (host, missing vl, bad base64, length, MD5 mismatch, unknown type) → `FiscalQrDecodeResult(null, "<reason>")`, never an exception. Tests build payloads with a small test-side builder (synthetic values, correct MD5) incl. refund, buyer id present, 592/848 lengths, corrupted byte → MD5 failure, wrong host.
2. `ZxingQrReader : IQrReader` — packages ZXing.Net + ZXing.Net.Bindings.ImageSharp (+ SixLabors.ImageSharp; check licences: ImageSharp's Six Labors Split License — acceptable for this non-commercial personal project? record the licence in the report; if unsuitable use ZXing.Net.Bindings.SkiaSharp instead and say why). Options: QR_CODE only, TryHarder, TryInverted, AutoRotate. On no result retry with the image downscaled to max 1600 px and upscaled ×2 (for tiny QRs). Returns the decoded text or null; never throws on a bad image (null + no crash). Tests generate QR images in-test (ZXing writer) with a synthetic URL: plain, rotated 90°, small inside a large white canvas, noise; and a non-image stream → null.
3. `FiscalJournalParser` (internal) — parses the journal text into ExtractedReceipt fields: PIB, business name, location (`id-name` line), address, city; item lines (name line possibly with `(Ђ)`/`(Е)` tax label and unit like `/KOM`, `/кг` then a numeric line `unitPrice quantity total` — decimal with comma or dot as printed; verify against the journal shape in the source project); `Укупан износ`/`Ukupan iznos`; payment lines (Платна картица/Platna kartica → Card, Готовина/Gotovina → Cash, Пренос на рачун/Prenos na račun → Transfer, Ваучер/Vaučer → Voucher, Друго безготовинско → Other; more than one non-zero → Mixed); `ПФР време`/`PFR vreme` (dd.MM.yyyy. HH:mm:ss, Europe/Belgrade → DateTimeOffset); `ПФР број рачуна`/`PFR broj računa`; `Бројач рачуна`. Refund receipts (`Укупна рефундација`). Both Cyrillic and Latin. Lines keep receipt order with 1-based Ordinal. Every amount decimal, parsed with InvariantCulture after normalising the separator. Tests: hand-written synthetic journals (made-up shop, PIB 123456789, plausible items) in Cyrillic and Latin, card/cash/mixed, refund, multi-line names, a journal whose line totals do not add up (parser reports what is printed — no correction).
4. `SufReceiptClient : IFiscalReceiptClient` — GET the payload's verification URL with `Accept: application/json`, User-Agent `noof-ledger/<version> (personal receipt lookup)`, timeout 15 s, `RemoveAllLoggers()` on the HttpClient. JSON: `invoiceRequest` (businessName, taxId, address, locationName…), `invoiceResult` (invoiceNumber, totalAmount, sdcTime…), `journal` (text) → parse the journal for lines/payments; prefer JSON fields for seller/number/time when present. Result: `FiscalFetchResult(receipt, null)` with Source FiscalQr, Currency RSD, QrTotal = payload.Total, VerificationUrl; failures (timeout, network, non-2xx, invalid JSON, journal without items) → `FiscalFetchResult(null, new FiscalFetchFailure(reason, statusCode))`, never throw except OperationCanceledException on the caller's token. Tests with a stub HttpMessageHandler: happy path (synthetic JSON + journal), 500, timeout, garbage JSON, request carries the Accept and User-Agent headers. Never call the real site in tests.
5. Logging: none of these classes log the full URL or `vl`; if you log, use [LoggerMessage] in sibling top-level classes and only the first 8 characters of `vl`.
Conventions: CLAUDE.md (public via interfaces; minimum accessibility; no comments explaining what; synthetic fixtures only — no real receipt, PIB of a real shop, or real vl ever enters the repo).
